# План интеграции оригинального Hermes Agent в DELNO

Дата: 13 ноября 2026. Статус: проект внедрения; оригинальный Hermes ещё не установлен в рабочем контуре DELNO.

## 1. Что именно внедряем

Используем upstream `NousResearch/hermes-agent` как движок рассуждения, долговременной памяти, задач по расписанию и делегирования субагентам. DELNO остаётся системой учётных записей, компаний, прав, коннекторов, базы знаний, CRM, звонков, заявок и интерфейса. Взаимодействие: DELNO API → приватный Hermes API `/v1/runs` → DELNO MCP gateway → данные/действия конкретной компании.

Нынешний `/opt/delno/api/app/operator/agent.py` — собственный синхронный цикл, а не upstream Hermes. Сохраняем его временно для существующих каналов и как аварийный откат; кабинет переводим на upstream первым. Телефонию и публичного помощника переводим отдельно после проверки задержек и сценариев.

## 2. Единицы изоляции

| Уровень | Объект DELNO | Объект Hermes | Граница |
| --- | --- | --- | --- |
| Компания | `tenant_id` | Отдельный `HERMES_HOME` / профиль и на первом этапе отдельный gateway/container | Память, сессии, skills, cron, секреты, журналы не смешиваются между компаниями. |
| Сотрудник компании | `user_id` и роль | Отдельная сессия и личный контекст внутри компании; при требовании личной памяти — отдельный профиль | Сотрудник не наследует полномочия владельца. |
| Агент компании | `agent_id` | Профиль/бот Hermes с выбранной ролью и своим набором инструментов | У компании может быть основной агент и постоянные специализированные боты. |
| Поручение | `task_id` | Hermes cron job либо run; для бизнес-состояния также запись DELNO | DELNO ведёт право владения, статус, аудит, лимиты, события и подтверждения. |
| Субагент | `parent_run_id` | `delegate_task` | Временный исполнитель, наследует только разрешённые родителю инструменты; не создаёт себе новые права. |

Практическое правило: один основной агент на компанию; у каждого сотрудника — личная сессия и свой набор разрешений. Если нужна независимая персональная память и персональные расписания, создаём отдельный профиль на пользователя. Нельзя выдавать всем сотрудникам один профиль владельца: Hermes хранит память на уровне профиля, и она попадёт в контекст других сессий того же профиля.

## 3. Почему отдельный runtime на компанию сначала

Upstream поддерживает много профилей в одном gateway. Его пользовательское руководство `multi-profile-gateways` говорит, что MCP-подключения разделены по профилям, но внутренняя страница `multiplexing-gateway` одновременно называет регистрацию MCP-инструментов process-global. Это противоречие требует проверки на закреплённой версии. Первый контур можно запустить с отдельным gateway/container на компанию. После теста A/B на разные каталоги инструментов и токены и замера памяти профили можно уплотнить в одном gateway. Права пользователей в любом случае обеспечивает DELNO, а не Hermes multiplex.

Один gateway на каждого *пользователя* не нужен по умолчанию: это дорого и затруднит общий контекст компании. Исключение — пользовательский агент с персональными секретами и памятью. Для сотрудников с разными ролями даже при общем агенте компании все DELNO MCP-вызовы должны идти через пользовательский scoped token, а не через полномочный ключ компании.

## 4. Идентичность и права

1. DELNO JWT на входе. `tenant_id`, `user_id`, `role`, `agent_id`, разрешённые connector accounts вычисляются сервером; модель не может прислать их в аргументах инструмента.
2. Для каждого Hermes run DELNO выдаёт краткоживущий scoped capability token с `tenant_id`, `actor_user_id`, `agent_id`, `run_id`, списком tool IDs, knowledge scopes, сроком и nonce. Токен передаётся MCP gateway через серверный канал. Долгоживущий `mcp_api_key` tenant не выдаётся агенту.
3. MCP `tools/list` возвращает только готовые и разрешённые для данного agent/run инструменты. `tools/call` повторно проверяет разрешения, конкретный connector account, лимиты и необходимость подтверждения. Публичное перечисление всех инструментов сейчас есть в `mcp_gateway.py`; его нужно изменить до подключения upstream.
4. Секреты почты, календаря, телефонии и мессенджеров хранятся в DELNO Vault. Hermes получает результат вызова, но не пароль или refresh token.
5. Внешнее действие с последствиями (отправить письмо, позвонить, изменить CRM/календарь) проходит политику подтверждений. Решение сохраняется в DELNO и возобновляет тот же Hermes run через `/v1/runs/{id}/approval`. Нельзя полагаться только на системный промпт.
6. Запрет прямого terminal/file/browser доступа из tenant runtime к `/opt/delno`, чужим профилям, БД и сетям внутренних сервисов. Даже если upstream умеет выполнять команды, бизнес-данные доступны только через scoped MCP. Egress allowlist и лимиты ресурсов.

## 5. Контекст и знания

- Общая база знаний компании живёт в DELNO Knowledge; поиск через MCP возвращает документы только своего tenant и разрешённого раздела с источником и версией.
- Память Hermes хранит предпочтения, незавершённые вопросы, рабочие выводы и сценарии конкретного агента. Она не подменяет CRM, календарь или базу знаний как источник истины.
- Контекст на запуск собирается слоями: базовые правила DELNO → профиль компании → роль агента → права пользователя → цель задачи → нужные выдержки из базы знаний → текущие данные коннекторов.
- Не загружать всю базу знаний и все прошлые диалоги в каждый запрос. Использовать поиск и ссылки на источники, ограничение по времени/объёму и обновление памяти после задачи.
- Временный субагент получает только явно переданную цель и выбранные выдержки; по документации upstream он не наследует всю историю родителя.

## 6. Задачи, события, расписание, субагенты

- Срок или период: Hermes `cronjob`, но DELNO сохраняет зеркальную запись `agent_tasks` с tenant, actor, расписанием, часовым поясом, статусом, лимитами и идентификатором cron job. Из кабинета пользователь может посмотреть, остановить и изменить задачу.
- Событие (новая заявка, сообщение, письмо): DELNO принимает webhook/poll result, проверяет tenant и idempotency key, записывает `PlatformEvent`, ставит агентный run через `/v1/runs`. Для заявок с сайта уже есть `lead.created`; для почты нужен подключённый polling/webhook, если провайдер не присылает события.
- Разовая долгосрочная задача: запись DELNO `agent_tasks` + Hermes run. Если работа должна продолжиться после рестарта, не полагаться на живой `delegate_task`: upstream прямо указывает, что делегирование привязано к родительской сессии/процессу. Долгую работу разбивать на durable этапы/запуски.
- Субагенты: Hermes `delegate_task` для ограниченных параллельных работ внутри одного поручения. Роли «исследователь», «работа с почтой», «CRM», «календарь» — шаблоны профилей/разрешений DELNO. Дочернему агенту нельзя расширить список инструментов, tenant, бюджеты или глубину делегирования.
- Постоянный специализированный агент = отдельный профиль/бот внутри tenant, а не субагент. Он может иметь свою память и расписания, но доступ к общим данным компании — только через DELNO MCP.

## 7. Контракт UI и API

Кабинет DELNO вызывает свой backend, не Hermes напрямую. Backend создаёт `/v1/runs` с idempotency key и сохранённой связкой `tenant_id/user_id/conversation_id ↔ Hermes profile/session_id/run_id`. Прогресс получает через Hermes SSE или polling и записывает в DELNO `agent_runs/agent_steps`; UI показывает «план», «проверяю данные», «вызываю инструмент», «ожидаю подтверждения», «завершено/ошибка». Показываем наблюдаемые действия и результаты, а не скрытые внутренние рассуждения модели. При обновлении страницы UI восстанавливается по DELNO БД и Hermes run status. Остановка и подтверждение пробрасываются через backend с проверкой владельца.

## 8. Этапы внедрения и критерии готовности

### Этап 0. Исследование upstream и изолированный прототип

Зафиксировать commit/tag upstream, лицензию, API, профили, cron, delegation, конфигурацию MCP, ограничения multiplex и обновлений. Развернуть отдельный контейнер без клиентских секретов. Проверить `/v1/runs`, прогресс, остановку, подтверждение, создание cron и субагента на тестовых инструментах. Результат — reproducible image и матрица совместимости. Рабочий DELNO не переключать.

### Этап 1. Граница компаний

Provisioning/retirement runtime per tenant: отдельный `HERMES_HOME` volume, сеть, credentials к модели, ресурсные лимиты, health check, backup. Карта `tenant_id ↔ runtime/profile` в DELNO БД. Две тестовые компании A/B с разными знаниями и коннекторами; автоматические проверки, что A не видит список, вызов, память, cron или историю B. Отказ runtime A не должен остановить B.

### Этап 2. Scoped MCP и коннекторы

Добавить таблицы `agent_profiles`, `agent_tool_grants`, `agent_connector_grants`, `agent_run_tokens`, аудит. Переделать `tools/list`, `tools/call` и `hermes.profile` на готовность и права; отказаться от широкого tenant owner key в работе Hermes. Сначала подключить read-only инструменты Knowledge, CRM/заявки, календарные слоты, затем записи через подтверждение. Каждый вызов содержит trace/run id и идемпотентный ключ.

### Этап 3. Кабинет и онбординг

Добавить настройку агента в кабинете: назначение, кто может им пользоваться, какие источники знаний и инструменты доступны, статус каждого коннектора, тестовый вызов. Новый владелец компании через чат получает пошаговые инструкции и формы подключения, агент видит readiness инструментов. Сохранить существующий интерфейс, сменить backend только для выбранного test tenant/feature flag. Сопоставить переписки и не потерять историю.

### Этап 4. Задачи и субагенты

Панель поручений, расписаний, истории запусков, бюджета и подтверждений. Проверить создание/остановку периодического поручения из естественного языка, событие `lead.created`, параллельное делегирование и восстановление после рестарта. Для почтового мониторинга сначала обеспечить надёжное входящее событие/опрос, затем дать агенту право читать и готовить ответ; отправка по политике компании.

### Этап 5. Каналы и голос

Telegram/MAX/email/web направлять в нужный tenant, agent и session; сохранять один корпоративный контекст и канал-специфичные правила. Телефонию переводить последней: измерить задержку ответа и реализовать короткий realtime контур для речи, который вызывает Hermes для задач и действий асинхронно. Не держать голосовой ответ на длительном агентном run.

### Этап 6. Эксплуатация

Набор тестов на утечку A→B, полномочия разных сотрудников, prompt injection из писем/файлов, недоступность коннектора, повтор webhook, рестарт worker, тайм-аут, ошибку отправки и превышение бюджета. Метрики: успешные задачи, подтверждённые действия, задержка, расходы на tenant/agent, сбои коннекторов. Обновления upstream — только с проверкой API/MCP и миграцией профилей, а не автоматическим обновлением production.

## 9. Решения, требующие проверки в прототипе

1. Поддерживает ли закреплённая версия Hermes безопасную передачу отдельного scoped токена для каждого run в MCP без утечки между сессиями. Если нет — нужен DELNO MCP proxy с отдельным endpoint/credential per tenant-agent и проверкой user/run на стороне DELNO; не патчить upstream наскоро.
2. Как выбранная версия сохраняет/возобновляет runs и cron после рестарта; какие события SSE гарантированы. DELNO держит собственный durable учёт бизнес-задач.
3. Можно ли настроить toolset и sandbox на профиль без process-global side effects. До доказательства — отдельный gateway на tenant.
4. Пределы ресурсов на сотни компаний. После безопасного MVP измерить память и CPU на idle/runtime и решить, нужен ли warm pool или проверенный multiplex.

## 10. Ресурсы и масштабирование

Текущий сервер DELNO: 8 vCPU, 15 GiB RAM, около 12 GiB available на момент проверки 13.11.2026; 197 GiB диска, из них 156 GiB свободно. Hermes на нём ещё не запущен, поэтому его фактическое потребление не измерено.

Для 10 компаний отдельные gateway могут быть приемлемы после замера одного idle профиля и типичного активного запуска. Для 100 компаний постоянный отдельный gateway каждой на этом сервере не закладывать: даже условные 150–400 MiB на процесс составят 15–40 GiB до памяти сессий и параллельных задач. Это сценарный расчёт, не измерение Hermes.

Контракт `tenant_id/agent_id/session_id` и DELNO MCP не должен зависеть от числа gateway-процессов. После тестов 2, 10 и 30 профилей выбираем уплотнение в один gateway или распределение профилей по нескольким узлам. Лимитируем одновременные запуски и субагентов на tenant, глубину делегирования, память кэша, токены и расходы. Фоновые задачи ставим в очередь, cron распределяем по времени. На 100 компаний понадобится проверенный multiplex и/или несколько узлов.

## 11. Минимальный первый результат

Для двух изолированных тестовых компаний: владелец открывает DELNO, видит своего Hermes, задаёт поручение «каждые 30 минут проверяй новые заявки», получает запись в списке задач, видит запуск и его действия, при перезапуске задача сохраняется. В компании B нет ни данных, ни задачи, ни доступных инструментов компании A. Затем подключаем реальную почту, календарь и остальные каналы по тем же правилам.
