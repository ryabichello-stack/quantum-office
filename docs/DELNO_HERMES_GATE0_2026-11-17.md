# DELNO × Hermes: Gate 0 — фактическое состояние

Дата: 17.11.2026. Проверка: Git `quantum-office` (`origin/main` `89c9758`), код `/opt/delno/api`, контейнеры и Postgres C4B `161.104.89.123`. Сервер проверен на чтение; этот аудит ничего в production не меняет. Секреты не выводились.

## Краткий вывод

Каркас общего Hermes уже существует: один работающий `delno-hermes-pool` обслуживает отдельные профили компаний. Это основа, которую следует развивать. Однако изоляция бизнес-инструментов **не доказана**: production разрешает постоянный MCP-ключ профиля без обязательной привязки к конкретному запуску. Память и автономные задачи Hermes в профилях практически пусты. Внешние сообщения Telegram/MAX обрабатывает отдельный Frontline-контур `run_operator_turn`, а не полноценный Owner Hermes. Эти два агента следует оставить разными по полномочиям.

## Расхождения с целевой моделью и приоритет

1. **P0 — изоляция инструментов.** Устранить зависимость от постоянного MCP-ключа в каждом запуске. Сначала инструментировать фактический `auth_via`, обеспечить run-scoped credential в Hermes MCP, параллельно проверить два профиля и отказ для чужого tenant/profile/run/tool. Затем включать строгий режим с откатом. Не включать `DELNO_MCP_DENY_LEGACY_KEY=1` сейчас: бизнес-инструменты могут остановиться.
2. **P0 — источник истины и выпуск.** Сравнить все prod-файлы и digest образов с Git, особенно V17 site, API и compose; зафиксировать, какие PR реально развернуты. Выстроить сборку/откат из commit. Иначе тесты репозитория не доказывают состояние сервера.
3. **P1 — Owner context.** Хранить факты компании, историю решений и цели с `tenant_id`, при появлении сотрудников ещё и `user_id`/ролью. Штатные Hermes memory/skills проверять на одном профиле и на перезапуске прежде, чем вводить новый сервис памяти. Корневых файлов MEMORY/USER и сохранённых заметок сейчас нет.
4. **P1 — события и длинные задачи.** `platform_events` уже существуют; проверить доставку, идемпотентность и восстановление после сбоя. `agent_tasks=0`; нельзя объявлять фоновую автономию работающей без E2E на создании задачи, исполнении, уведомлении и рестарте.
5. **P1 — Frontline.** Отдельный публичный агент с опубликованной KB и узкими правами. Его качество сейчас ниже Owner Hermes: ограниченный набор инструментов и нет устойчивого плана/памяти. Улучшать качество в рамках Frontline без прямого доступа к gateway владельца. Hermes может готовить изменения в KB/сценариях, а публикация должна проходить контролируемо.
6. **P2 — нативные skills, делегирование, онбординг.** Провести capability probe на v0.23.2, затем подключать подтверждённые возможности к DELNO с tenant scope и проверкой полномочий. Не создавать новую очередь, БД памяти или субагентный runtime по одной лишь гипотезе.

## Уточнённые этапы и условия перехода

1. **Gate 0 (этот аудит).** Согласовать границу Owner/Frontline, приоритет P0 и порядок. До следующего этапа не менять production архитектуру.
2. **Gate 1 — безопасность.** Instrumentation auth path, scoped MCP, тест двух компаний на одном воркере и конкурентных вызовов, отрицательные тесты, план отката; только затем отказ от legacy ключа.
3. **Gate 2 — Agent Context.** Проверить родную память Hermes, связать с DELNO tenant/user scope и подтвердить «продолжим вчерашнее» после рестарта.
4. **Gate 3 — Event Engine.** Из существующих `platform_events` сделать надёжный маршрут в разрешённую задачу, персональное уведомление и аудит.
5. **Gate 4 — цели и делегирование.** Использовать подтверждённые native-механизмы Hermes, долговечный статус и восстановление после перезапуска.
6. **Gate 5 — skills и автономность.** Изолированное хранение, проверенная публикация навыка и контроль прав инструментов.
7. **Gate 6 — онбординг.** Пройти путь нового клиента с произвольной целью; каналы, телефон и календарь подключаются только по потребности. Затем улучшать Frontline отдельным потоком.

## Что ещё не проверено в Gate 0

Не проводились реальные параллельные вызовы инструментов двух компаний, тест восстановления backup, нагрузочный тест, чтение содержимого `state.db`, проверка активной cron-доставки, полноценный новый пользовательский онбординг через интерфейс, фактическая доставка ответов публичных ботов, проверка всех 29 инструментов. Это не основания считать их неисправными; это границы доказательств данного отчёта. Первый шаг после согласования — закрыть P0 с трассой MCP и воспроизводимыми тестами.

Локальный запуск `test_run_bindings_mcp.py`, `test_hermes_nous_scope.py`, `test_tenant_isolation.py` остановился при сборе: системный Python Mac не содержит `sqlalchemy`/`httpx`. В runtime-контейнере DELNO тестовые файлы не упакованы. Поэтому этот Gate 0 не засчитывает их как выполненные; следующий этап должен запускать их в воспроизводимом test image/venv из Git.
