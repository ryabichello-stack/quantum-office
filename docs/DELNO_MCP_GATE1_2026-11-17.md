# DELNO × Hermes — Gate 1: MCP-изоляция

Дата: 17.11.2026. Ветка `codex/delno-mcp-gate1`. Цель — сделать вызов бизнес-инструментов зависимым от конкретного запуска, компании, профиля, пользователя и списка разрешённых инструментов.

**Текущий итог:** первый rollout был остановлен из-за потери контекста в `Session Authority`. Исправление `b2c7cf6` привязало token к фактическому admitted turn. После нового поэтапного rollout API работает из `5053e3ef`, Hermes Pool — из образа `gate1-b2c7cf6`; все четыре защитных флага включены. 13 production бизнес-событий после ограничения — все `auth_via=run_token` с `run_id`, от двух компаний. Реальные параллельные диалоги обеих компаний и фоновая задача вызвали MCP под собственным run; legacy ключ получил 403. Telegram/MAX health и 15 тестов каналов прошли. Отчёт и backup: `docs/AGENT_CHANGE_REGISTER.md`, `/opt/delno/backups/gate1-fix-20261117/`. Дальнейшие разделы фиксируют историю проверки и первоначальный план; их формулировки «production не изменён» относятся к состоянию до rollout.

Ключи не выводились, инструментов и записей на production эта проверка не вызывала. Это подтверждает действующий legacy path, но не доказывает межтенантную утечку.

## Изменения в коде

1. MCP gateway проверяет хэш токена, tenant, actor, роль, agent, grants и профиль против binding. В строгом режиме обязательны `X-Delno-Run-Id` и `X-Delno-Profile-Id`; отсутствующий, чужой, отозванный или просроченный run отклоняется. Смешанные заголовки (токен A + ключ B) отклоняются.
2. Diagnostics `/hermes-nous/run-tokens` теперь выключена по умолчанию; доступ возможен только platform admin при отдельном флаге `DELNO_MCP_DIAGNOSTIC_MINT=1`. Завершение, ошибка и остановка запуска отзывают токен и binding; авторизация также сверяет терминальный статус `agent_runs`.
3. Событие `mcp.tool_called` содержит только `auth_via` и `run_id` для проверки миграции; сам токен не логируется.
4. Точный патч upstream Hermes revision `ae2a81ccc00e` (v0.23.2) связывает токен и профиль с одним turn через `ContextVar`. В режиме `DELNO_MCP_RUN_SCOPE_ENABLED=1` вызовы `delno_office` идут напрямую во внутренний MCP endpoint с этими заголовками. Другие MCP-коннекторы не меняются. Нет контекста запуска — нет вызова.
5. `DELNO_MCP_LEGACY_CATALOG_ONLY=1` позволяет прежнему ключу получить схемы инструментов при старте Hermes, но запрещает ему исполнять бизнес-инструменты. Это переходная совместимость, а не окончательное удаление ключа. Отдельный безопасный метод discovery без долгоживущего ключа понадобится позднее.

## Дополнительный review и восстановление backup (17.11)

Security review обнаружил ещё пять путей: JWT мог исполнить бизнес-инструмент без run scope; diagnostic mint мог создать привязанный к несуществующему Hermes run токен; завершённый run оставлял токен действующим до TTL; legacy binding не требовал profile header и не перепроверял роль; задача без владельца исполнялась с ролью `tenant_owner`. Изменение роли или удаление владельца прерывает последующие вызовы и задания. Разрешения внутри уже идущего вызова не отменяются задним числом.

## Финальный изолированный прогон обновлённого PR (17.11)

На C4B отдельно от production собраны `delno-hermes-runtime:gate1-final-ed593a2` из точного upstream v0.23.2 с патчем PR и `delno-api:gate1-final-lab` из той же ветки. Внутренняя Docker network `delno-gate1-final`, одноразовая SQLite, две компании, четыре запуска: Owner и системный background в каждой компании. Установленный Hermes выполнил `_RunLaunch → _run_agent_sync → MCP handler → HTTP` параллельно (24 запуска). Серверный `platform_events` зафиксировал 26 бизнес-вызовов, все 26 с `auth_via=run_token`, непустым верным `run_id`, только двумя ожидаемыми tenant и четырьмя ожидаемыми run. Фоновому запуску не выдан `send_mail_draft`; попытка вызова получила 403. Отдельный тест реального пути планировщика подтверждает, что задача без владельца выбирает `system_event`, а роль владельца перечитывается перед очередным запуском.

Отрицательные HTTP-проверки: legacy MCP-key не исполняет бизнес-инструмент (403), просроченный token (401), завершённый run (401), чужой profile (403). Подмена run/token/profile через установленный Hermes handler также отклонена. Вызовы Owner-профиля в том же цикле получили собственные данные и не затронули фоновые/чужие grants.

Проверка обнаружила дополнительный риск, присутствующий в текущем production коде: `get_tenant_summary` возвращал весь `tenant.settings`, включая постоянный MCP-key и хэши run tokens; `update_tenant_settings` мог заменить служебные поля и возвращал/аудировал полный словарь. В PR оба инструмента ограничены явным списком публичных бизнес-полей (`assistant_name`, `greeting`, `business_note`, `legal`). Повторный изолированный прогон подтвердил отсутствие `mcp_api_key` и `run_tokens` в ответе. Production пока **остаётся уязвимым** до согласованной выкладки; постоянный ключ следует ротировать после перехода, как указано ниже.

После этой правки локальный API набор: **449 passed, 1 deselected**. Тесты используют реальные установленные модули Hermes и HTTP MCP gateway, но `Agent.run_conversation` в стенде заменён контролируемым вызовом инструмента, чтобы результат не зависел от внешней LLM. Поэтому естественный разговор Owner Hermes с моделью и работа внешних каналов в этом стенде **не проверялись**; они обязательны в staged/prod smoke по плану ниже. Gate 1 не закрыт.

## Порядок безопасной выкладки после отдельного согласования

До первого изменения: сохранить digest текущих `delno-api` и `delno-hermes-pool`, compose и `.env` с правами 0600, `pg_dump` и согласованный snapshot обоих Docker volumes (`/data/hermes`, `/data/hermes-profiles`). Восстановление DB и profile volume в отдельном окружении проверено выше; перед фактической выкладкой повторить на свежем snapshot. Не писать секреты в журнал.

1. Развернуть API-код с **нулевыми** Gate 1 флагами. Проверить старый путь, Frontline, Telegram, MAX, кабинет, `/health`.
2. Собрать и запустить patched Hermes image с `DELNO_MCP_RUN_SCOPE_ENABLED=0`. Проверить, что старая работа сохранилась.
3. Включить только `DELNO_MCP_RUN_SCOPE_ENABLED=1` у Hermes. На двух тестовых компаниях выполнить параллельно разрешённые и запрещённые инструменты. По событиям `mcp.tool_called` убедиться, что все бизнес-вызовы `auth_via=run_token` с соответствующим run ID.
4. Включить `DELNO_MCP_REQUIRE_RUN_BINDING=1` в API. Повторить два тенанта, подмены и штатные сценарии. Проверить запуски по расписанию; diagnostic mint должен отвечать 403.
5. Одновременно включить `DELNO_MCP_LEGACY_CATALOG_ONLY=1` и `DELNO_MCP_DENY_LEGACY_KEY=1` в API. Проверить, что Hermes видит полный каталог, но старый ключ получает 403 на бизнес-вызов; Frontline продолжает работать.
6. Не очищать постоянные ключи профилей до следующей миграции discovery. Не включать флаги по отдельности в ином порядке.

**Smoke на каждом шаге:** `/health`, вход в кабинет и запуск Hermes для двух тестовых компаний, реальные разрешённые/запрещённые MCP calls, Frontline, Telegram, MAX и задача по расписанию. В логах/событиях каждый бизнес-вызов должен иметь `auth_via=run_token` с верным run ID, tenant и profile; одновременно тестовый постоянный ключ должен получить 403 на бизнес-инструмент. Одного HTTP 200 недостаточно. **Стоп:** любой чужой tenant в ответе, успешный бизнес-вызов legacy ключом, отсутствие run ID в событии, ошибка реального Hermes, рост 401/403 штатных клиентов или сбой фоновых задач. При стопе прекратить переключение и выполнить откат.

**Откат:** сначала вернуть `DELNO_MCP_DENY_LEGACY_KEY=0`, `DELNO_MCP_LEGACY_CATALOG_ONLY=0`, `DELNO_MCP_REQUIRE_RUN_BINDING=0`; затем `DELNO_MCP_RUN_SCOPE_ENABLED=0`. Проверить старый вызов и два tenant smoke. Если проблема в новом коде/образе — вернуть сохранённые digest/compose; если повреждены данные — восстановить свежие DB/volume snapshots в maintenance window и сверить counts/профили. Миграций БД в PR нет. Обратное переключение флагов проверено локально; реальный rollback production по-прежнему требует отдельного разрешения.

## Если скомпрометирован постоянный MCP-ключ

До включения строгих флагов его обладатель может исполнять все 76 инструментов **своей** компании вне конкретного run. Это позволяет читать её данные и делать разрешённые инструментами действия; межтенантный доступ не доказан, но возможен ущерб внутри компании. После включения catalog-only + deny он сможет получать схемы/служебные сведения профиля, но не исполнять бизнес-инструменты и не использовать `run_id` как обход. Он не должен получать `mcp_api_key` из scoped/JWT profile API.

Ротация после доказанного перехода: (1) отозвать активные run bindings и токены затронутой компании; (2) выпустить новый tenant MCP-key, записать в сейф/профиль без вывода в лог; (3) атомарно обновить profile `.env` и перезапустить только соответствующий профиль/воркер по безопасной процедуре; (4) проверить старый ключ = 401, новый = только каталог, а бизнес-вызов = только `run_token`; (5) просмотреть события вызовов и уведомить владельца при подозрении на злоупотребление. Не ротировать все ключи одновременно и не делать это в рамках PR #121 без отдельного согласования.

## Критерий завершения Gate 1

Production smoke и журналы подтвердили scoped авторизацию реальных бизнес-вызовов, отказ legacy ключу, изоляцию двух компаний и работу фонового задания. Gate 1 закрыт для проверенного контура. Ротация постоянных ключей остаётся отдельным согласуемым действием. Редкий пустой ответ Hermes в одном прогоне требует отдельной диагностики качества диалога и не меняет результат проверки MCP-изоляции.
