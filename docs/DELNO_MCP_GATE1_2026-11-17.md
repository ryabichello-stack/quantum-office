# DELNO × Hermes — Gate 1: MCP-изоляция (кандидат, без выкладки)

Дата: 17.11.2026. Ветка `codex/delno-mcp-gate1`. Production не изменён. Цель — сделать вызов бизнес-инструментов зависимым от конкретного запуска, компании, профиля, пользователя и списка разрешённых инструментов, сохранив безопасный переход для работающего пула.

## Проверенные находки

| Находка | Доказательство | Последствие до исправления |
|---|---|---|
| Hermes v0.23.2 не переносит заголовки `create_run` в свой MCP-клиент | `bridge.py` выдаёт `X-Delno-Run-Token`, но `profile_homes.py` задаёт MCP `Authorization: Bearer ${DELNO_MCP_KEY}`; поиск по установленному `/opt/hermes-agent` не нашёл обработки заголовков DELNO | Обычный вызов использует постоянный ключ профиля и может обходить grants конкретного запуска. Этот ключ сам привязан к компании; факт утечки **между** компаниями не обнаружен, но отсутствие per-run ограничений доказано конфигурацией. |
| Legacy можно было оставить с полным каталогом и вызовами | Production `DELNO_MCP_STRICT=0`, `DELNO_MCP_DENY_LEGACY_KEY` не задан; `mcp.py` | Обладатель ключа профиля может вызвать инструмент без run token. |
| Строгий режим можно было переопределить `DELNO_MCP_LEGACY_KEY_META_ONLY=0` | Ветвление `mcp.py` до исправления | Некорректная комбинация настроек возвращала полный доступ legacy при включённом strict. Исправлено: strict имеет приоритет. |
| Run token проверял запись в `tenant.settings`, но не всегда сверял активную binding-запись, профиль и текущего пользователя | `run_tokens.py`, `run_bindings.py`, `mcp.py` | Отзыв binding сам по себе не останавливал токен; смена роли или компании пользователя не проверялась при вызове. Исправлено с флагом обязательной binding. |
| `run_id + ключ компании` использовался как совместимый путь | `mcp.py` | Внутри одной компании постоянный ключ мог воспользоваться разрешениями чужого запуска, если известен run ID. При `DELNO_MCP_DENY_LEGACY_KEY=1` этот путь теперь отклоняется. |

Read-only проверка production `/v1/mcp/tools` для двух существующих тестовых компаний `onboard-audit-a-0ba32868` и `onboard-audit-b-0ba32868`: обе получили HTTP 200, `auth_via=mcp_api_key`, по 76 инструментов. Ключи не выводились, инструментов и записей на production эта проверка не вызывала. Это подтверждает действующий legacy path, но не доказывает межтенантную утечку.

## Изменения в коде

1. MCP gateway проверяет хэш токена, tenant, actor, роль, agent, grants и профиль против binding. В строгом режиме обязательны `X-Delno-Run-Id` и `X-Delno-Profile-Id`; отсутствующий, чужой, отозванный или просроченный run отклоняется. Смешанные заголовки (токен A + ключ B) отклоняются.
2. Diagnostics `/hermes-nous/run-tokens` создаёт binding по тем же правилам. Остановка запуска отзывает токен и binding.
3. Событие `mcp.tool_called` содержит только `auth_via` и `run_id` для проверки миграции; сам токен не логируется.
4. Точный патч upstream Hermes revision `ae2a81ccc00e` (v0.23.2) связывает токен и профиль с одним turn через `ContextVar`. В режиме `DELNO_MCP_RUN_SCOPE_ENABLED=1` вызовы `delno_office` идут напрямую во внутренний MCP endpoint с этими заголовками. Другие MCP-коннекторы не меняются. Нет контекста запуска — нет вызова.
5. `DELNO_MCP_LEGACY_CATALOG_ONLY=1` позволяет прежнему ключу получить схемы инструментов при старте Hermes, но запрещает ему исполнять бизнес-инструменты. Это переходная совместимость, а не окончательное удаление ключа. Отдельный безопасный метод discovery без долгоживущего ключа понадобится позднее.

## Проверки в изолированном окружении

- HTTP E2E на локальном FastAPI и SQLite: два тенанта, 24 параллельных обращения, собственные ответы, запрет чужого профиля/run ID/ключа и неразрешённого mail tool. Также проверены JSON-RPC, отзыв binding, смена компании/роли пользователя, mixed credentials, режим discovery и обратное переключение флагов.
- Патч применён к локальной копии исходников точно того commit, который установлен на C4B; `py_compile` прошёл, повторное применение отказало. Изолированный образ `delno-hermes-runtime:gate1-test` собран на C4B **без изменения работающего пула**. Gateway ответил `/health=200` с версией 0.23.2; чужой ключ профиля дал 401, верный — 404 для несуществующего run. Текущий OAuth не имеет права изменять GitHub Actions workflow, поэтому задача сборки не добавлена в CI.
- На отдельной internal Docker network, с временными профилями и SQLite API, исполнен код **установленного патченного Hermes**: `_run_agent_sync` → `_make_tool_handler` → реальный HTTP → новый DELNO MCP gateway. 24 параллельных запуска двух компаний получили только собственный tenant ID. Запуск без контекста отклонён; подмена run/token/profile получила 403; неразрешённый `send_mail_draft` получил 403. Legacy ключ увидел каталог, но не смог исполнить бизнес-инструмент.
- MCP/tenant/Frontline tests: 32 целевых теста и 33 теста Telegram/MAX/widget прошли. Полный API набор с исключением одного внешнего DNS-теста: **443 passed, 1 deselected**. При запуске всех тестов `test_suggest_reachable_host_fixes_quantum_typo` не прошёл из-за недоступности внешнего DNS с Mac; изменённый код в нём не участвует.
- Откат флагов проверен на том же тестовом SQLite DB: после перезапуска отдельного API без строгих флагов ключи обеих компаний снова вызвали старым режимом инструмент с HTTP 200. Производственные контейнеры и volumes не менялись. Полный LLM-диалог, failover и восстановление production snapshot пока не проверены.
- GitHub PR #121: штатные `delno-api` и `delno-knowledge` checks завершились успешно. Проверки сборки Hermes image в штатном workflow нет.

## Порядок безопасной выкладки после отдельного согласования

До первого изменения: сохранить digest текущих `delno-api` и `delno-hermes-pool`, compose и `.env` с правами 0600, `pg_dump` и согласованный snapshot обоих Docker volumes (`/data/hermes`, `/data/hermes-profiles`). Проверить чтение snapshot и команду восстановления в отдельном окружении. Не писать секреты в журнал.

1. Развернуть API-код с **нулевыми** Gate 1 флагами. Проверить старый путь, Frontline, Telegram, MAX, кабинет, `/health`.
2. Собрать и запустить patched Hermes image с `DELNO_MCP_RUN_SCOPE_ENABLED=0`. Проверить, что старая работа сохранилась.
3. Включить только `DELNO_MCP_RUN_SCOPE_ENABLED=1` у Hermes. На двух тестовых компаниях выполнить параллельно разрешённые и запрещённые инструменты. По событиям `mcp.tool_called` убедиться, что все бизнес-вызовы `auth_via=run_token` с соответствующим run ID.
4. Включить `DELNO_MCP_REQUIRE_RUN_BINDING=1` в API. Повторить два тенанта, подмены и штатные сценарии. Проверить запуски по расписанию и диагностику.
5. Одновременно включить `DELNO_MCP_LEGACY_CATALOG_ONLY=1` и `DELNO_MCP_DENY_LEGACY_KEY=1` в API. Проверить, что Hermes видит полный каталог, но старый ключ получает 403 на бизнес-вызов; Frontline продолжает работать.
6. Не очищать постоянные ключи профилей до следующей миграции discovery. Не включать флаги по отдельности в ином порядке.

**Откат:** сначала вернуть `DELNO_MCP_DENY_LEGACY_KEY=0`, `DELNO_MCP_LEGACY_CATALOG_ONLY=0`, `DELNO_MCP_REQUIRE_RUN_BINDING=0`; затем `DELNO_MCP_RUN_SCOPE_ENABLED=0`. Проверить старый вызов и 2 tenant smoke. Если проблема в новом коде/образе — вернуть сохранённые digest/compose, затем `/health` и два пользовательских сценария. Миграций БД в этом PR нет. Локальный тест проверил обратное переключение флагов; реальное восстановление snapshot в отдельном окружении должно пройти **до** выкладки на production.

## Критерий завершения Gate 1

Код и штатный CI зелёные, изолированный реальный Hermes MCP путь и откат флагов проверены. Перед production нужны review PR, согласованный snapshot и проверка восстановления volumes/DB в отдельном окружении, затем отдельное разрешение владельца на выкладку и production smoke с `auth_via=run_token` у каждого бизнес-вызова. Пока последние условия не исполнены, переход к Gate 2 не объявлять.
