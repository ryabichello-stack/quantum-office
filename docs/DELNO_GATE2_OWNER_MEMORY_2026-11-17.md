# DELNO Gate 2: долговременная память Owner Hermes

Дата: 18.11.2026. Статус: PR #122 в работе; Gate 2 развёрнут на production API и веб-интерфейсе, включён только для audit-компании до финального переключения.

## Реализация

- PostgreSQL хранит короткие проверенные факты, решения, отклонённые варианты, цели, проекты, задачи и темы разговоров с ключом `(tenant_id, user_id)`. Сырой текст диалогов, ответов инструментов и документов не копируется в таблицы памяти.
- Факты извлекаются моделью только из сообщения владельца. До записи действуют проверка формата, ограничение размера, фильтры секретов, персональных контактов и инструкций. Ошибка извлечения не прерывает диалог.
- При изменении решения прежнее значение остаётся в истории записи, но не попадает в актуальный контекст. Удаление/исправление/запрет темы очищают краткие темы разговоров и меняют идентификатор сессии, чтобы прежний контекст Hermes не вернулся из кэша.
- Контекст ограничен 6000 символами, выбирает до 16 релевантных фактов и шесть тем. Текущие бизнес-данные MCP имеют приоритет. Переписка Telegram/MAX, почта и CRM не импортируются в личную память.
- Реальный путь кабинета `/v1/operator/chat` и прямой `/v1/hermes-nous/runs` используют один сервис памяти. Чат Hermes и его история теперь видны только пользователю, которому они принадлежат; общие бизнес-каналы остаются общими.
- В кабинете есть панель просмотра, исправления, удаления, полной очистки, запрета и снятия запрета. API расположен под `/v1/hermes-nous/memory/*` и требует JWT.
- Профильная встроенная память Hermes (`MEMORY.md`/`USER.md`) отключается в `config.yaml`: она не имеет пользовательского scope. Перед включением флагов нужно обновить существующие профили и доказать отсутствие чужих файлов памяти.

## Включение и откат

Миграция `010_hermes_owner_turns` создаёт таблицы памяти и назначает владельца старым диалогам Hermes только там, где у компании ровно один пользователь. Старые диалоги компаний с несколькими пользователями скрыты до отдельного безопасного разбора владельца.

Память требует `DELNO_OWNER_MEMORY_ENABLED=1` в API и флаг `hermes_owner_memory` у конкретной компании. Глобальный флаг включён после миграции; флаг компании включён только для audit A. Откат: выключить tenant-флаг, вернуть прежние образы и конфиги профилей, при необходимости восстановить БД из бэкапа. Таблицы памяти не удалять при быстром откате.

Девять профилей Hermes переведены на `memory_enabled: false`, `user_profile_enabled: false`; файлов `MEMORY.md`/`USER.md` в профилях нет.
- CI PR #122 на `f86e9d2` зелёный. Локально 459 тестов прошли, один ранее существующий тест внешней доступности `quantumpayouts.ru` упал из-за сети тестовой машины.
- Полный реальный E2E через `/v1/operator/chat` и модель: A, B, C, E прошли; после перезапуска и готовности Hermes Pool D, F, G, H прошли. Два тестовых tenant, включая второго пользователя в A, не видят чужую личную память и диалог. Ранний факт удержался после семи других диалогов. Удалённый факт не всплыл в новом разговоре. Вредная инструкция не была сохранена. Реальные данные MCP победили устаревшую запись в памяти.
- Smoke Gate 1 на текущем API: Owner и фоновое задание отвечают, Telegram/MAX доступны, legacy business MCP возвращает 403, бизнес-вызовы авторизуются scoped run token (`business_events=2`, `matching_run_events=1`).
- Первый запрос сразу после `docker restart` попал в период запуска Hermes и не вернул ожидаемый факт; после ожидания готовности тот же тест прошёл. В процедурах проверки после restart обязательно ждать готовности пула.

Осталось включить tenant-флаг для рабочего профиля, проверить его отдельно, зафиксировать финальный smoke и слить PR. До этого Gate 2 не считать закрытым.
