# DELNO Gate 2: первая часть долговременной памяти Hermes

Дата: 17.11.2026. Статус: код в отдельной ветке; production не менялся.

## Что сделано

- Завершённые диалоги владельца с Hermes сохраняются в PostgreSQL по `tenant_id`, `user_id`, `session_id` и `run_id`. Повтор того же запуска не создаёт вторую запись.
- В следующий диалог этого же пользователя передаётся короткая история последних разговоров, в том числе из другой сессии. История помечена как справочные данные; актуальные бизнес-факты и права по-прежнему проверяются через MCP.
- История ограничена шестью записями и 6000 символами. Очевидные значения `Bearer`, `dmcp_`, `password/token/пароль: ...` удаляются перед сохранением. Секреты должны вводиться через формы сейфа, а не через чат.
- `GET /v1/hermes-nous/memory/turns` позволяет увидеть свои записи; `DELETE` по тому же пути удаляет их. Чужой пользователь или компания не видит эти записи.
- Весь новый путь выключен по умолчанию. После миграции `010_hermes_owner_turns` нужны оба переключателя: `DELNO_OWNER_MEMORY_ENABLED=1` на API и флаг `hermes_owner_memory` для выбранной компании. Сначала включается только audit-компания, затем проверяются живой разговор «о чём говорили вчера», удаление и изоляция двух компаний.

## Границы этой части

Это эпизодическая память разговоров владельца. Hermes также имеет встроенные `MEMORY.md`/`USER.md`, но текущие профили DELNO не содержат сохранённых карточек. Унифицированный контекст из Telegram/MAX, почты, CRM и задач, выделение долговечных фактов, управление сроком хранения и интерфейс памяти в кабинете — следующие части Gate 2. Эти каналы не надо смешивать с личным диалогом владельца без отдельной модели прав и согласований.

## Проверки

- Два теста: новый диалог получает вчерашний контекст; повторный run не дублируется; чужой tenant и второй пользователь компании не видят историю; список и удаление работают.
- 20 существующих и новых тестов Hermes/изоляции прошли в изолированном API-контейнере.
- Миграция 009 → 010 выполнена на восстановленной копии production PostgreSQL. Пустая база выявила старый дефект миграций 001 → 002 (`party_cache` создаётся дважды); новый шаг 010 этот дефект не затрагивает.
